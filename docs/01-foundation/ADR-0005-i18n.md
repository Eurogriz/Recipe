# ADR-0005: Internationalization (i18n) with Babel

**Status:** Accepted
**Date:** 2026-06-24
**Deciders:** Архитектор, UX Lead

---

## Context

The application must support two languages from MVP:
- **Russian** (default — primary market is Russia/CIS)
- **English** (international market, scientific terminology)

All UI strings, error messages, menu items, dialog text must be translatable.

## Decision

**Babel + gettext with .po/.mo files.**

## Rationale

1. **gettext is the standard:** Mature, well-documented, supported by all translation tools (Poedit, Weblate, Crowdin).
2. **Babel:** De-facto Python standard for i18n, integrates with Flask, Django, Pyramid, and any custom app.
3. **Compile-time messages:** .mo files are compiled binary, fast at runtime.
4. **Locale-aware formatting:** `babel.numbers`, `babel.dates` for number/date formatting per locale.
5. **Translation memory:** Compatible with professional translation workflows.

## Implementation

### Directory Structure

```
locales/
├── ru/
│   └── LC_MESSAGES/
│       ├── messages.po    # source translations (editable)
│       └── messages.mo    # compiled binary (generated)
├── en/
│   └── LC_MESSAGES/
│       ├── messages.po
│       └── messages.mo
└── babel.cfg              # extraction config
```

### Extraction

```bash
# Extract translatable strings from source code
pybabel extract -F babel.cfg -o locales/messages.pot .

# Update translations
pybabel update -i locales/messages.pot -d locales -l ru
pybabel update -i locales/messages.pot -d locales -l en

# Compile
pybabel compile -d locales
```

### Usage in Code

```python
from infrastructure.i18n import _

# Simple translation
title = _("recipe.editor.title")  # "Редактор рецептуры" / "Recipe Editor"

# With formatting
error = _("recipe.validation.cas_invalid", cas="7732-18-X")
# RU: "Некорректный CAS номер: 7732-18-X"
# EN: "Invalid CAS number: 7732-18-X"
```

## Locale-Aware Formatting

```python
from babel.numbers import format_decimal, format_currency
from babel.dates import format_datetime

# Numbers (comma vs period as decimal separator)
format_decimal(3.14, locale="ru")  # "3,14"
format_decimal(3.14, locale="en")  # "3.14"

# Dates
format_datetime(dt, locale="ru", format="short")  # "24.06.2026"
format_datetime(dt, locale="en", format="short")  # "6/24/26"
```

## Translation Workflow

1. Developer writes English strings in source code (`_("...")`)
2. CI extracts to .pot template
3. Translators (professional or community) translate to Russian
4. Compiled .mo files bundled in installer

## Consequences

### Positive
- Standard, well-supported translation workflow
- Compatible with professional translation tools
- Locale-aware number/date formatting
- Easy to add new languages later (de, fr, zh, etc.)

### Negative (mitigated)
- **Initial translation effort:** Russian translations for ~500-1000 strings
  - **Mitigation:** Can be parallelized; partial translations OK during MVP
- **String freeze:** Harder to refactor strings once translated
  - **Mitigation:** Babel extraction on every CI build catches missing strings
